# AI-Infrastructure-GCP

Highly available, containerized RAG application on Google Cloud Platform (COP3604).
The infrastructure is built from one Python script; the application runs as Docker
containers on a Compute Engine VM, with its database on LVM volumes.

> Status: infrastructure and database are working on GCP. The web, AI inference,
> load balancer and monitoring parts are still to be built. See [Status](#status).

## How it fits together

```
 Internet --(80/443 only)--> [ GCE VM: rag-vm ]
                               |  Docker Compose (florida-poly-dining/compose.yml)
                               |   - MariaDB 11.8 (internal network only, no published ports)
                               |   - web, inference, load balancer (planned)
                               |  LVM volume group rag_vg on a separate data disk
                               |   - db     -> /data/db  (database files)
                               |   - models -> /models   (model weights)
 Secrets: GCP Secret Manager -> fetched by the VM at boot (never stored in git)
 SSH: only through Identity-Aware Proxy (IAP)
```

## Repository layout

| Path | What it is |
| --- | --- |
| `scripts/deploy.py` | One-command GCP build: network, firewall, secrets, VM |
| `scripts/startup.sh` | Runs on the VM at every boot: Docker, LVM, secrets, containers. Safe to re-run |
| `scripts/lvm-snapshot.sh` | Takes (or removes) an LVM snapshot of the database volume |
| `tests/check_ports.sh` | Proves from outside the VPC that database/inference ports are blocked |
| `tests/results/` | Saved test logs |
| `florida-poly-dining/` | The application: `compose.yml`, database init SQL, data, helper scripts |

## How to run it

You need a GCP project with billing linked. Everything below runs in **Cloud Shell**
(the terminal icon at the top right of console.cloud.google.com), which already has
`gcloud`, `git` and Python.

```bash
# 1. Point gcloud at your project (use the Project ID, not the name)
gcloud config set project YOUR_PROJECT_ID

# 2. Get the code
git clone https://github.com/ratsrichie/AI-Infrastructure-GCP.git
cd AI-Infrastructure-GCP

# 3. Preview what will be created (changes nothing)
python3 scripts/deploy.py all https://github.com/ratsrichie/AI-Infrastructure-GCP.git --dry-run

# 4. Build everything
python3 scripts/deploy.py all https://github.com/ratsrichie/AI-Infrastructure-GCP.git
```

The VM needs about 5 more minutes after the script finishes. Watch its progress:

```bash
gcloud compute ssh rag-vm --zone us-central1-a --tunnel-through-iap
sudo tail -f /var/log/rag-startup.log      # ends with "=== startup finished ..."
```

Then check it (use `sudo` for the LVM commands):

```bash
sudo lvs                       # db and models volumes in rag_vg
df -h /data/db /models         # both mounted
sudo docker ps                 # mariadb should be "healthy"
```

### Other commands

| Command | What it does |
| --- | --- |
| `python3 scripts/deploy.py status` | Show the VM and its IP |
| `python3 scripts/deploy.py stop` | Stop the VM to save credits (disks keep a small charge) |
| `python3 scripts/deploy.py start` | Start it again; the startup script re-checks everything |
| `python3 scripts/deploy.py network`, `firewall`, `secrets`, `vm <repo-url>` | Run one step only |
| `--machine e2-standard-4` | Use a bigger VM for load tests (default is e2-small to save credits) |
| `--dry-run` | Print the `gcloud` commands without running them |

Re-running `deploy.py` is safe: it skips anything that already exists.

### Updating the code on the VM

- **Application code (the repo):** push to GitHub, then reboot the VM or run
  `sudo google_metadata_script_runner startup` on it. The startup script pulls the latest code.
- **`startup.sh` itself:** the VM keeps its own copy, uploaded when the VM was created.
  After changing it, run:
  ```bash
  gcloud compute instances add-metadata rag-vm --zone us-central1-a \
    --metadata-from-file startup-script=scripts/startup.sh
  ```
  then reboot the VM.

### Run the tests

From Cloud Shell, not the VM:

```bash
bash tests/check_ports.sh $(gcloud compute addresses describe rag-ip --region us-central1 --format='value(address)')
```

Ports 3306, 5432, 11434 and 22 must show PASS (closed). Port 80 shows FAIL until the web
tier exists. Logs are saved in `tests/results/`.

## Rules for everyone

- **Never commit secrets.** No passwords, keys, tokens, `.env` files or Terraform state.
  Passwords are generated by `deploy.py`, stored in Secret Manager, and written to
  `florida-poly-dining/secrets/` on the VM at boot. That folder is in `.gitignore`.
- Optional but recommended: `pip install pre-commit && pre-commit install` to run a
  secret scan (gitleaks) before every commit.
- Pin container image versions. Never use `latest`.
- Every container needs CPU and memory limits.
- Only ports 80 and 443 may be open to the internet. Never publish the database or inference ports.
- Make small, frequent commits under your own name. The git log is part of the grade.
- Stop the VM when you are not using it: `python3 scripts/deploy.py stop`.

## Known notes

- The database uses the subfolder `/data/db/mariadb` of its LVM volume, because a fresh ext4
  volume contains `lost+found`, which would stop MariaDB from initializing.
- The default VM is an e2-small (2 GB RAM) to save credits. It is too small for two inference
  replicas; use a larger machine type for AI work and tests, and stop the VM afterwards.
- `florida-poly-dining/scripts/setup.sh` creates passwords for local testing only. On GCP the
  startup script uses Secret Manager instead.
- Adapted from the observability project's `deploy/gcp_setup.sh` (network, firewall and VM logic).
